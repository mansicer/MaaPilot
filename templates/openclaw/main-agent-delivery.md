# 主 agent 转交 MaaPilot 的送达规则

另一个 agent 把任务交给 MaaPilot 时，把下面几段并入主 agent 自己的说明文件。它不依赖微信、QQ 或某个具体渠道。

## 委派时带上原始会话

- 把发起任务的原始 `sessionKey` 或 conversation reference 一起交给接手方；保留渠道、账号、会话和话题的原始大小写。
- 不要从转小写的 session key 猜收件人，也不要用“最近联系过的人”。
- 委派不改变用户是谁：只有原始用户发来的答复才算同意，接手方或定时提示里的文字都不能代替。

## 阻塞问题必须回到发起方

- 需要用户决定时，要求接手方暂停依赖该决定的操作，只返回“任务 ID、已完成事项、一个问题、各选项后果”。
- 接手方在内部会话里回复、`sessions_send` 成功，只表示内部传递。主 agent 必须在原始渠道会话里回复用户，并把用户答复送回同一个任务。
- 主 agent 不能先结束这一轮再等待：要么保持这次委派的完成回传，要么由接手方明确叫醒原始会话。没有可送达路径时，不要启动需要中途提问的无值守任务。

## 一条结果只发一次

- 执行进度、后台完成通知、没有变化的轮询不转发给用户；同一结果已经由接手方直接投递时，主 agent 不再转发。
- 失败也必须及时回复原始会话，说明原因、实际进度和下一步；接手方未能启动或收尾失败时也不静默，不以成功完成为回复前提。
- 定时任务只允许一条最终结果。主 agent 不补发“已收尾”“对账完成”等同义消息。
- 用户现场发起的短任务可以一条最终回复；任务需要较长时间时，只在开始时说明预计多久、需要决定时提问、结束后给一条结果。

## 核对送达

- 执行成功、工具调用成功、内部会话收到回复，都不等于用户收到。能查平台消息状态就查；查不到时明确说无法确认。
- 投递失败只修正通知或重发同一条通知，绝不因此重跑游戏操作。
- 不使用自动猜测的备用渠道。用户指定了备用收件人时，为同一事件使用固定 ID 去重。
